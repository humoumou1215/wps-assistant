1. 普通测试和真实测试有什么不同？

命令谁在回答？它主要检查什么？
npm test假 Add-in（测试替身）检查 MCP 服务能否发请求、收响应、处理错误。它不证明 WPS API 真能用。
npm run test:wps-live真的 WPS ET 和 WPP检查真实文档能否打开、Add-in 能否连接，以及 API 操作和读回是否正确。
npm run test:wps-writer-live真的 WPS Writer单独检查临时 DOCX 的正文/表格读取、Render 写入与读回。

这次跑出来：npm test 通过；真实 WPS 冒烟测试也通过。两种测试各做各的工作，不能拿前者冒充后者。

2. 测试脚本具体做了什么？

  1. 先检查安全条件。必须是 macOS；WPS 要先完全退出；测试端口默认是 18767，不能被别的程序占用；原 Add-in 静态页面服务 18766 必须可访问。
  2. 编译项目。运行 npm run build，把 TypeScript 服务编译成 JavaScript。
  3. 建一个临时房间。脚本在系统临时目录创建独一无二的文件夹，测试状态文件也只放在这里，不用家里的正式状态文件。
  4. 把测试流量送到独立端口。临时调整 Add-in 的 WebSocket 目标为 127.0.0.1:18767。结束时会还原 addon/main.js。
  5. 启动测试 MCP 服务。服务只用临时数据目录，并同时提供 MCP HTTP 接口和 WPS Add-in WebSocket 接口。
  6. 生成临时测试文件。create-fixtures.py 制作 `.xlsx`、`.pptx` 和 `.docx` 输入文件。这些是固定测试输入，不是伪造的 WPS API 返回值。
  7. 真的打开 WPS。ET/WPP 和 Writer 使用独立命令；脚本用 macOS 的 open 打开临时文件，并轮询 MCP 等待对应 Add-in 注册。
  8. 做题和检查。使用 MCP 客户端调用 workspace.list_documents、document.get、wps.exec、Transform 和 Render。
  9. 清理。修改只写入临时文件副本；脚本保存副本、关闭 WPS、停止测试服务并删除临时目录。若 WPS 没有正常退出，脚本会保留临时目录，避免删掉 WPS 仍在使用的文件。

端口小知识：WPS 现有注册的 Add-in 页面仍从 18766 取静态文件；这次真正的 MCP 和 WebSocket 测试流量走独立的 18767。不是把正式文档发给测试服务。

3. 练习册里放了什么？ 📚

ET 表格练习册

  • 工作表叫 MCPProbe。
  • A1 是 WPS_MCP_SEED，B1 是数字 7。
  • B2 有公式 =1+2，预期计算结果为 3。

WPP 演示练习册

  • 有 1 张幻灯片。
  • 有一个文字形状，里面写着 WPS_MCP_SEED_TEXT。

Writer 文字练习册

  • 正文包含 WPS_WRITER_SEED，另有一个表格和单元格标记。

Python 脚本只负责把这些固定输入包装成 WPS 能打开的 Office 文件。WPS 打开文件之后，读出来的内容和 API 操作结果才是本次真实测试的观察结果。

4. ET 测试：先读，再写，再读回来 ✏️

第一次查询时，测试会确认 WPS 当前打开的文件路径就是这次的临时副本，并读取工作表、单元格、公式和应用版本。

const book = Application.ActiveWorkbook;
const sheet = Application.ActiveSheet;
return {
  app: Application.Name,
  version: String(Application.Version),
  workbook: book.Name,
  sheet: sheet.Name,
  seed: sheet.Range("A1").Value2,
  formulaValue: sheet.Range("B2").Value2
};

预期答案：工作表是 MCPProbe，A1 是 WPS_MCP_SEED，B2 算出 3。

接下来用 Transform 准备一个小变量，再用 Render 在临时表格的 Z100 写入公式、粗体和数字格式：

const cell = Application.ActiveSheet.Range("Z100");
cell.Formula = "=1+2";
cell.Font.Bold = true;
cell.NumberFormat = "0.00";
return {
  formula: cell.Formula,
  value2: cell.Value2,
  bold: cell.Font.Bold,
  numberFormat: cell.NumberFormat
};

最后再用只读查询读一次 Z100。测试要求：公式仍是 =1+2、数值是 3、粗体为 true。这叫写入—读回检查，不是只看 WPS 有没有报错。

5. WPP 测试：在临时幻灯片上加一个文字框 🖼️

先确认演示文稿路径、幻灯片数量和种子文字；然后用 Render 在第一张幻灯片新增文本框：

const slide = Application.ActivePresentation.Slides.Item(1);
const box = slide.Shapes.AddTextbox(1, 30, 40, 210, 60);
box.TextFrame.TextRange.Text = variable.value.token;
box.Left = 30;
box.Top = 40;
box.Width = 210;
box.Height = 60;
return {
  text: box.TextFrame.TextRange.Text,
  left: box.Left,
  top: box.Top,
  width: box.Width,
  height: box.Height
};

读回检查文字标记，以及左、上、宽、高是否正确。写入发生在这次的临时 `.pptx` 副本，不会改用户正式演示文稿。

6. Transform 和 Render 是什么？

工具小孩版解释这次怎么用
transform.create写一张“读取说明卡”。保存只读 JavaScript 代码。
variable.transform照说明去 WPS 读取东西，装进小盒子。取得测试 token，或读取工作簿的数据。
render.create写一张“修改说明卡”。保存有意要写入临时文档的代码。
variable.render真正照修改卡去做，然后报告结果。写公式、改格式、加文本框。

项目规定：wps.exec 和 Transform 用来读；有意修改文档的操作放在 Render。测试也遵守这条规则。

8. 小朋友自己想再跑一次？▶️

  1. 在 macOS 上，先把 WPS 完全退出。
  2. 确认项目原来的 Add-in 页面服务在 127.0.0.1:18766 可访问。
  3. 确认 WPS 和测试端口 18767 没被其他程序占用。
  4. 在项目目录运行：
    npm run test:wps-live
  5. 如果 18767 被其他程序占用了，可以换一个非 18766 的端口：
    WPS_LIVE_PORT=18769 npm run test:wps-live
  6. Writer 单独运行：
    npm run test:wps-writer-live
    同样要求 WPS 完全退出；脚本会单独打开 Writer 测试文档并在结束时关闭 WPS。
  7. 看到绿色的通过结果后，测试脚本会自动清理临时文件。普通模拟测试仍用 npm test。

如果说“WPS 已经运行”：先完整退出 WPS 再重试。
如果说 Add-in 页面服务不可用：先检查 curl http://127.0.0.1:18766/health。
如果说 WPS 没注册文件：检查 WPS 是否能加载本机 Add-in，以及测试服务日志；不要把“没连上”算作 API 通过。

9. 还有哪些没测？ 🧩

  • Writer 冒烟测试只覆盖正文和表格读取、文本插入与读回；完整的 105 项 Writer 报告矩阵仍未逐项运行。
  • 这是一轮冒烟测试，只挑几个常用 API 检查，不是把 WPS 的几千个成员全部调用一遍。
  • 本轮由 Python 创建可打开的临时 Office 输入文件；没有把 Workbooks.Add() 或 Presentations.Add() 当作本轮断言。
  • 事件监听的回调内容、其他 WPS 版本、更多 API 参数组合，仍需后续逐项加入测试矩阵。

就像先确认自行车能刹车、能转弯，再慢慢测每个零件；冒烟测试是第一圈，不是整本 API 字典的毕业考试。

# UI 规范对照检查（2026-09-30）

> 后续修复与复查结果见 [UI 修复与原型复查](ui-fix-validation-2026-09-30.md)。本报告保留修复前的文字检查结论；历史截图已从工作区移除，可从清理前的 Git 提交查看。

结论：服务端和工具链的主要架构已经实现，但正式页面只沿用了原型的部分样式，多个核心交互被简化或遗漏。不能把“11 项测试通过”或旧报告中的“P0–P2 已落地”理解为原型完整验收通过。

这是修复前的历史检查记录，原工作区未记录提交号。以下代码行号、测试数量和页面行为只对应当时快照；不用于判断当前代码是否仍有同一缺陷。

- 浏览器实际检查正式页面、原型、引用选择器、刷新后的历史以及两个独立页面间的同步。正式页面按 400px 任务窗格宽度检查。

### A1：写入事实在 JSON 里，但工具卡摘要没有兑现设计承诺

规范明确写道：“工具调用卡必须完整呈现写入事实（目标文档 / 写入位置 / renderId / 耗时）”，这是“不设写入二次确认”的配套要求。

当前完成卡的可见摘要只有类似 `variable render · 完成 · 5 ms`。展开后把参数和结果拼成一段 JSON；成功结果确实包含目标名、description、renderId，因此不是服务端完全缺少这些数据，而是前端没有将它们组织为人能直接核对的写入事实。执行前的 `variable.render` 参数通常只有 variableId，连目标都看不到。

建议：为 Render 生成稳定的事实摘要，例如“已写入 UI验证.xlsx › 销售数据!D3 · render_001 · 2 ms”；多条写入逐条显示成功/失败，原始参数、结果和代码留在详情。不要依赖模型最终文字替代工具证据。

验收：只有 variableId 的调用也能从绑定状态解析目标；结果返回后更新真实结果；部分失败时明确列出已经写入和失败的项。

### A2：Markdown 被当成普通文本

原型支持表格、列表、加粗、行内代码和代码块；正式页的实时答复和历史答复使用 `textContent`，未接入 Markdown 呈现。

浏览器发送测试消息后，`**重写已完成**`、`| 对象 | 结果 |` 和反引号都原样显示。表格没有成为表格，代码没有对应样式。这是实际阅读能力缺失，不只是字体差异。

建议：使用经过转义和限制的轻量渲染，保持零前端构建约束；流式和历史共用同一个渲染器。不要直接把模型文本写入未处理的 innerHTML。

验收：同一条含表格、加粗、代码的答复在生成结束和重开页面后呈现一致。

### A3：会话数据落盘了，恢复 UI 没有恢复完整过程

`history()` 只提取 assistant 内容里的 text，跳过 thinking 和 toolCall；toolResult 被作为独立折叠卡放在会话中，未与原始 toolCall 按 toolCallId 配对。

同一轮刷新前存在“思考过程”和“完成 · 5 ms”，刷新后思考消失，工具卡只剩工具名和完成状态，参数也不再显示。检查 GET `/api/chat` 确认 thinking、toolCall.arguments、toolCallId、工具结果仍在历史中。部分成功 Render 的 lastRun 耗时也在结果里，恢复页没有利用。

建议：把 pi 历史转换为与流式页面相同的回合/过程块模型，按调用 ID 配对。区分工具调用总耗时与某条 Render 的耗时；缺少历史总耗时的数据应明确处理，不能拿当前 state 的最新执行覆盖历史。

验收：生成结束、刷新、服务重启三个状态下，思考内容、参数、结果、写入事实和分组保持可追溯。

### A4：时间顺序和回合分组没有沿用原型

原型在执行时按顺序追加思考、工具和文本，结束后把过程收进“过程详情 · N 条 · M 次工具调用”，最终答复留在外面。

正式页创建 assistant 时先创建正文 body，再在其后追加过程。最终答复因此显示在思考/工具前面。`thinking ||= ...` 将同一轮所有思考增量写进一个卡片：工具前后的两段思考被拼接，无法辨别各自发生的位置。`turn.end` 不做过程分组，也没有调用数量摘要。

这与历史恢复后的布局又不同：恢复时工具结果位于最终答复前，同一轮重开页面会改变呈现顺序。

建议：按消息/模型调用边界创建独立思考块和文本块；结束后执行统一的回合归组。若现有 SSE 不足以表达边界，增加很薄的消息边界事件，不必重写执行链。

### A5：变量页藏起了原型要求常驻的 Render 信息

原型 Render 行在不展开代码时就显示：目标文档、写入位置、renderId、上次写入时间、耗时及“重写”按钮。原型还专门标注“常驻展示 · 点 › 看写入代码”。

正式页折叠行只有 `render_001 · UI验证.xlsx`。位置、执行时间和单条重写按钮都在 details 内；用户必须先展开才能核对目标和执行。卡片头也没有上次重写摘要，只有另起一行的上次重算。

建议：常驻保留 Render 行及单条操作，仅折叠代码/详细事实。缩短日期展示，完整日期和耗时放 tooltip，恢复原型的密度。

说明：当时正式变量页和原型变量页的截图数据不同，仅对照布局和可见交互，不作同数据的像素一致性比较。

### A6：结构化引用已接通，但丰富交互没有保留

已实现：文档、选区快照、变量、Render 四类真实目录，文字筛选、部分键盘选择、可移除标签、结构化 refs 和服务端 ID 校验。

与原型的差异：

- 没有“全部 / 文档 / 选区 / 变量 / Render”分类和计数，也没有分类切换快捷键。
- 没有拼音全拼/首字母匹配，当前只对 label 做 substring 匹配。
- 没有悬停或点击固定的对象预览；不能在引用处查看选区数据、变量值、Render 目标/代码。
- 正文使用 textarea，标签在输入框上方单独保存。选中引用时删掉正文里的 `@...`，不保留引用对应的文字或位置。复杂的“把 A 写到 X、把 B 写到 Y”表达会失去对象在句子中的关联位置。
- 发送后的引用变成普通 `@ 标签` 文字，不再是可预览的 chip。
- `send()` 要求正文非空；只有引用标签的输入不会发送，而原型允许 refs 非空的消息。

建议：先补分类和引用预览；保留正文里的可辨识对象标签/位置，再完善拼音匹配。结构化 refs 通道继续使用现有实现。

### A7：变量页信息密度和预览退化

- 统计条只有“全部 N”和来源文件标签，没有 Render 总数、未绑定变量数、各文件变量数。
- 数值 chip 仅显示“数值”，没有原型的 `数值 770,450` 等快速摘要。
- 所有当前值统一输出 JSON；二维数据不呈现表格，标量也要展开才看得到。对于对象数组，需要明确列与行的推导规则。
- 当前值与 Transform 分成两个折叠项，不再是点击卡头展开统一数据详情；来源、描述、重算时间分占多行，卡片明显更疏。
- 代码没有原型的语法着色；原型的筛选条滚轮横移和边缘提示更新也未接通。

其中千分位数值与表格预览可由真实 value 推导。百分比不能无条件从普通数字猜测单位，需明确格式约定后再展示，不能照抄原型的静态类型标签。

### A8：入口窗格复用已做，但两份页面状态会过时

`main.js` 以 page 为缓存键，助手与变量入口分别创建窗格。旧报告明确接受了这种行为，现有 addon 测试也要求“两个入口创建两个 pane”，因此“两 pane”本身属于已记录的取舍，不能直接认定为违约。

问题在于两份页面都提供会话和设置页，却只在启动时读取会话和配置；切换页签不重读，2.5 秒轮询和“刷新”按钮都只请求 `/api/state`。

浏览器复现：第二页面先打开，在第一页面完成“第二面板同步验证”，第二页面切到会话并点击“刷新”，新消息仍不可见（对应文本节点数量为 0）。必须重载整个页面才能看到。另一个窗格修改配置时也存在同样的本地状态过时问题，后续保存可能覆盖新配置。

建议：优先让两个入口复用同一 UI 窗格并切到目标页签；若继续保留两个窗格，至少在页签进入/重新显示时同步历史与配置，并保护未保存表单。服务端单会话无需增加多会话设计。

### A9：官方模式的部分高级表单是无效控件

`formConfig()` 对两种模式都提交 api、thinkingFormat、maxTokensField；高级区也没有在 builtin 模式隐藏或禁用这些控件。

但 `buildRuntime()` 仅在 custom 模式将 api 与 compat 注册到 provider；builtin 模式直接取得 DeepSeek 内置模型，未应用这些字段。用户在官方模式里改变协议/思考格式/输出字段并保存，表单值会持久化，却不会改变实际请求。Headers 在最后应用，因此 Headers 不属于这个问题。

建议：按“官方只填 key、参数来自内置目录”的设计，把不支持的覆盖项设为只读/隐藏并说明；如果确实要支持覆盖，则测试保存字段与最终请求一致。

## 次要差异与判断限制

1. **上下文占用未实现**：原型有上下文条与百分比；生产页替换为最后一次模型调用的 tokens。移除静态 12% 是正确取舍，但后者不能代表真实上下文占用，也不能代表整轮用量。本次两次模型调用各 120 tokens，顶部显示“本次模型调用 120 tokens”，这个文案本身准确，只是没有提供原型的上下文能力。`turn.end` 目前也没有暴露正常 stopReason/willRetry。
2. **设置摘要精简**：缺少 provider、Base URL 和最大输出等原型摘要信息。编辑过程中仍显示已保存配置，比将未保存草稿称为“当前生效”更准确；这部分不建议为追求一致而倒退。若需要预览，明确标成“待保存”。思考支持提示未像原型一样动态更新。
3. **消息元信息简化**：原型有用户消息时间、复制/引用入口和逐消息模型名，正式页没有。原型“复制/引用”按钮只有展示、未见实际点击处理，应记录为设计元素缺失，不能称为已经实现又被删除的功能。
4. **批量反馈按变量计数**：正式页成功/失败按 `/api/actions` 请求计数，一次请求可能包含多条 Render；部分成功时请求整体失败，摘要不报告已经成功写入的 Render 数量。原型按 Render 条数汇总。建议增加明确单位和部分成功明细。
5. **余额与价格**：原型测试结果显示模拟余额，内置能力区展示价格；生产实现没有余额接口和价格展示。设计最终表单规范没有将余额明确列为必验项，因此属于增强能力缺失，不与 A1–A3 同级。
6. **收起按钮**：原型有自绘收起按钮，正式页移除。WPS 宿主是否提供足够的关闭/收起控件需要真实 Windows WPS 检查，本次不能断言用户无法收起。

## 已符合或合理变化的部分

- 三个消费者复用 `src/tools.ts`；MCP、内嵌 pi 和 UI 没有新增文档执行链。
- 内嵌 pi 固定版本、仅八个 customTools、关闭内置 shell/文件工具；数据目录与 pi 全局配置隔离。
- `/api/state`、`/api/actions`、SSE 会话、配置保存和连接测试已实现；变量重算/重写确实走工具。
- sourceRef、真实取值、Render/Transform 代码、执行元数据、连接状态、断开禁用和错误反馈已接通。
- 密钥/Headers 脱敏、同端点保留、换端点清除、停止、守卫修复上限、重启恢复等已有验证。
- 静态前端、无框架与前端构建步骤符合要求。
- 移除假 WPS 外壳、演示重播、固定连接状态、示例变量、随机执行耗时和虚构余额是正确的生产化处理。
- 外部 Agent 进度镜像、多会话、图片上传、provider CRUD、模型发现属于明确延后/排除项，不算本次缺陷。
- 连接测试从 GET `/models` 改为一次最小模型请求更能证明基础对话可用；真实 WPS 及所有端点协议兼容性仍需各自验收。

## 建议修复与验收顺序

1. 先统一流式与历史的回合模型，补齐写入事实卡与历史恢复（A1/A3/A4）。
2. 补安全 Markdown 呈现（A2），覆盖表格、代码和重开页面的一致性。
3. 恢复 Render 常驻行、变量统计及值预览（A5/A7）。
4. 完善引用分类、预览和正文关联（A6）。
5. 处理双窗格同步及无效设置字段（A8/A9）。

现有 11 项自动测试主要覆盖只读守卫、MCP/API、pi 工具回路、取消、配置隐私和重启数据恢复。`ui.integration.test.mjs` 并没有启动浏览器或断言页面 DOM。因此测试通过不能覆盖本报告中的 UI 差异。

下一次验收应至少包含：多模型调用与思考交错、Markdown 表格、只有 variableId 的重写、多个 Render 的部分失败、刷新后的完整过程、两个入口间的历史/配置同步，以及 360–400px 窄窗格中的常驻写入信息。

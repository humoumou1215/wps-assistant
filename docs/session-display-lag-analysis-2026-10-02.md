## 具体问题

### 1. 流式更新重建整个聊天 DOM，能丢失折叠点击

`addon/taskpane.js:813–816` 对流式事件调用 scheduleRender；`699` 仅按动画帧合并调用；`683–696` 对全部历史重新生成 HTML，并赋给 chatInner.innerHTML。已经结束的消息、折叠工具参数、所有思考正文也一起重新序列化并创建节点。

requestAnimationFrame 合并同一帧的事件，未将更新限制在当前发生变化的节点，持续流式输出仍可能每帧重建一次。

使用原始渲染函数和实际会话内容，在隔离的 Ego Chromium 页面验证：先展开目标思考卡片，派发真实鼠标按下事件，中途执行一次 renderTurns，再派发鼠标松开事件。卡片仍然展开；无中途重绘的对照点击能够收起。重绘后旧 details.isConnected=false，新旧节点不相同。

这证明节点替换能导致与第一张截图一致的点击失效机制；没有原窗格的输入事件 trace，不能证明截图那次点击一定发生了这个事件顺序。

### 2. 大文本反复解析和布局，折叠状态仍有成本

`addon/taskpane.js:680` 即使思考卡片收起，也将完整思考正文放入 HTML；每次更新都会转义、生成、解析整份正文。`696` 读取 scrollHeight 并写 scrollTop，还可能同步触发布局。

按会话第 50 行状态重放，生成 HTML 约 268,364 字符。5 次连续、全部思考卡片收起的同步 renderTurns 测量约 6.1–9.5 毫秒；展开 51,944 字符卡片后一次测量约 14.4 毫秒。仅用于说明当前实现的成本，不是原 WPS 窗格的性能数据。

较大的同步批量重绘测试曾触发浏览器评估超时；缩小为单次与 5 次后可完成。该压力测试不能当作真实 WPS 已发生长时间主线程阻塞的证据。

### 3. 展开/收起与内部滚动状态处理不完整

`addon/taskpane.js:684,695` 只记录并恢复已展开卡片，不保留节点、焦点或 thinking-text.scrollTop。重放中内部 scrollTop 从 190 变成 0。流式期间会反复回到正文开头，阅读体验不稳定。

`688` 对没有正文 text 的已完成过程组默认添加 open；恢复时又只处理展开状态。因此用户将这类组收起后，下一次重绘会自动展开。重放已验证。此问题是过程组层级的问题，不能直接等同于截图中的单个思考卡片失效。

### 4. 收起后的状态无法反映持续生成

`addon/taskpane.js:680` 只显示思考开头 100 个字符，超过后摘要基本不变；`691` 的“正在处理…”是静态文字，没有本阶段计时、最近输出时间或进度计数。现有 CSS 包含动效样式，但该渲染路径未使用相应指示元素。

`src/agent.ts:336–344` 只向客户端转发 text/thinking delta，没有转发工具参数生成阶段的进度；`src/api.ts:155` 的 15 秒 keepalive 是 SSE 注释，前端 `taskpane.js:812` 会跳过它。

因此第二张截图中，模型在长时间思考或准备工具参数时，用户可能只看到长时间不变的一行，无法判断还在生成还是连接异常。现有日志没有逐 delta/首 token/客户端最后收到事件时间，无法还原截图时的精确网络状态。

## 建议修复顺序

1. 保留每个 turn/block 的稳定 DOM，只更新当前流式文本节点；先解决鼠标点击、焦点、滚动被重绘打断的问题。
2. 收起时仅更新摘要、字符数和阶段状态；长正文展开时再加载，流式正文可按适当频率批量追加，避免每次重建历史。
3. 按稳定 key 保存用户明确的展开与收起状态；保留内部滚动位置并尊重用户暂停跟随。
4. 显示思考/准备工具/执行工具阶段、阶段耗时、最后一次收到输出的时间和累计输出；将服务 keepalive 与模型实际输出时间分开，避免把连接存活误当作模型进展。
5. 添加不含正文的性能遥测：delta 数量/长度、首输出与最长事件间隔、重绘耗时、长任务、连接终止原因。需要在 WPS 嵌入窗格中采集 trace，验证具体优化收益。
6. 将过量思考与 5 分钟整轮截止策略纳入模型层面优化评估。降低思考预算可能减少等待，但无法修复上述 DOM 交互缺陷。

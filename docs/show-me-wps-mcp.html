Agent 怎么会写 WPS API？

不是 MCP 教它，也不是 Server 把 WPS API 再封装一遍。Agent 先读项目提供的 Skill / Reference。

Skill / Reference

这是 Agent 的“WPS API 说明书”

里面告诉 Agent：WPS JS API 有哪些对象、怎么读工作簿/幻灯片/图表、常见代码怎么写，以及哪些操作必须放进 Render。

1Agent 读取 Skill / Reference
知道 Application、Workbook、Worksheet、Presentation、Shape、Chart… 怎么用
2Agent 自己生成 JavaScript

3代码交给 wps-mcp
查询代码 → wps.exec　　提取代码 → Transform　　写入代码 → Render
4Add-in 在 WPS 里执行
MCP 不把它翻译成另一套“自创 WPS API”。
所以项目能保持简单： WPS 已经有一套很大的 API。我们只需要教 Agent 会用它，而不是复制它。

两条护栏，就够了

不是把 WPS API 包得很厚，而是只把“读”和“写”的边界说清楚。

想看，可以直接看

Agent 先根据 Skill / Reference 写出只读的 WPS JS API 代码，再通过 wps.exec 执行，了解表格、幻灯片、选区、图表等内容。

workspace.list_documents → document.get → wps.exec

想改，必须走 Render

Agent 也直接写 WPS JS API，但所有会修改文档的代码必须成为 Render，再由正式执行入口运行。前置条件是 Variable 已经跑过一次 Transform、手里有值。这样写能力强，边界仍然简单。

transform.create → variable.transform
render.create → variable.render → WPS
被拦下来的时候，一次说清

判据集中在 src/readonly-guard.ts，违规一次性全部报出，每条带行列号、源码行和改写建议 —— 拿到就能一轮改完，不用“报一条、改一条、再报一条”。

你写的为什么被拦
o.a = 1任何成员赋值都拦。判据是纯语法的，不区分文档对象和你自己声明的本地对象。
i++ · --i自增自减一律拦，本地循环计数器也不例外。写成 i = i + 1 就通过了。
new Date()所有 new 都拦，内置构造器（Date / Map / Set / RegExp）一样在内。
arr.sort()方法黑名单按属性名匹配：读一下就拦，本地数组也中招。换个属性名，或者挪进 Render。
记住这个方向： 上面这些写法在 Render 里全部合法 —— Render 的代码根本不经过这道守卫。所以“想改文档”不要跟守卫较劲，直接写成 Render。
老实说一句：“只读”来自 Acorn 静态检查——拦住成员赋值、new、删除和常见写入方法，属于 best-effort，不是 JavaScript 沙箱，绕过去仍然可能写出有副作用的代码。真正有写权限的只有 Render，所以只运行可信代码。

怎么把它接上？

顺序不能反：先起服务，再注册 Add-in，最后完全重启 WPS。细节见 README。

Step 1 · 起服务

只监听本机

一个进程同时提供 MCP（stdio + Streamable HTTP）、Add-in 资源和 WebSocket，默认端口 18766，只绑定 127.0.0.1。

npm ci && npm run build && npm start
Step 2 · 注册 Add-in

写进 publish.xml

把 ET / WPP / WPS 三个本地 Add-in 注册进去；脚本只增删自己的条目，改前先备份，也可 --uninstall 回滚。

node scripts/install-addin.mjs
Step 3 · 接 MCP 客户端

填这个地址

传输方式选 Streamable HTTP。客户端要跑在能访问本机 loopback 的环境里。

http://127.0.0.1:18766/mcp
Step 4 · 验证

先问服务，再看文档

健康检查通了、WPS 里能列出 documentId，才算接通。注意：注册后必须完全退出并重启 WPS（托盘图标也要退）。

curl http://127.0.0.1:18766/health

给开发者：代码只认 4 个目录

这是职责地图，不是鼓励把项目拆成很多层。目录名可以调整，但边界最好别混。下面这棵树是目标形状；v0.1 的实现还很集中。

Developer mental model

读代码时，先问：这件事属于谁？

Skill / Reference 教 Agent WPS JS API；Server 管 MCP、规则和路由；Add-in 只负责在 WPS 里执行；Shared 只放最小协议。Agent 不在这 4 个目录里——它是外面的使用者。

Skill = 教 WPS API
Agent = 想 + 写 WPS API 代码
MCP Server = 管代码 / 规则 / 路由
readonly-guard = 只读判据的唯一来源
WPS Add-in = 执行代码
WPS = 真正的文档

├─ skills/            # Agent 的“WPS API 说明书”
│  ├─ SKILL.md         # 什么时候读、什么时候写、调用约束

职责分布：谁拥有哪件事？

边界越清楚，项目越不容易从“小桥”长成“大平台”。

Agent

理解自然语言，按需读取 Skill / Reference，直接生成 WPS JS API 查询代码、Transform 代码和 Render 代码。

关键点：不是调用一套“封装好的 WPS 业务 API”，而是自己写 WPS JS API。

MCP Server

暴露少量工具、登记文档、保存 Agent 写好的代码规则、按 documentId 找到正确的 Add-in。

拥有：Variable / Transform / Render 的定义与执行入口。

WPS Add-in

待在真实 WPS 进程里，接收执行请求，直接运行 Agent 生成的 WPS JS API 代码。

不负责：理解用户意图，也不自己发明 Transform / Render。

WPS

真正拥有工作簿、幻灯片、选区、图表、样式和当前编辑状态。

事实来源：文档内容以 WPS 当前状态为准。

开发时，最重要的 3 个“不”

这三个地方一旦破坏，项目就会迅速变复杂。

不要复制 WPS API

不要为每个 WPS JS API 再包一层 MCP Tool。Skill / Reference 负责“教”，Agent 负责直接生成 WPS JS API 代码。

不要让查询偷偷写

wps.exec 和 Transform 都应该是只读。文档修改只有 Render 一个正式入口。

不要把 Agent 塞进运行时

同步执行是确定性的程序流程：Transform → Variable → Render，不应该每次都重新问模型。

Simple means powerful.

wps-mcp 不想成为另一个 Office 框架。
它只想用 Skill 教 Agent 写 WPS API，让 Agent 能找到 WPS、看懂 WPS、保存 Transform / Render，然后在正确的时候执行这些代码。

不复制整套 WPS API 不发明新的复杂 DSL 不让 Agent 参与日常计算 不把桥变成大脑

v0.1 明确不做
